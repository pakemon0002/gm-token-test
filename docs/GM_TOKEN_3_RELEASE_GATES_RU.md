# GM TOKEN 3.0 — блокирующие проверки перед настоящим ботом
Дата проверки: 2026-11-11. Этот документ — список фактических проверок и незавершённых работ, а не сертификат безопасности.

## P0 — хранение игровых данных
- [ ] **Не переносить текущую Render SQLite из временной файловой системы в публичный режим.** Узнать фактический путь DB_PATH, установить постоянное транзакционное хранилище и регулярные проверяемые резервные копии.
- [ ] **Supabase project gm-token (Postgres)** содержит существующие записи игроков, кошельков, транзакций, daily_rewards, holding и прочих модулей. Ничего не удалять/не сбрасывать и не смешивать с тестовой базой.
- [ ] Выписать соответствие таблиц Postgres и SQLite: users, wallets, journal, pools, mining state, upgrades, daily_claim, points, trades, orders, tasks, boxes, referrals, support; описать миграцию schema/data и версионирование.
- [ ] Проверить транзакционную согласованность и 1:1 ledger before/after migration; провести восстановление из бэкапа в изолированной среде; проверить два одновременных API-запроса.
- [ ] Техническая миграция Postgres должна переносить серверную транзакционную бизнес-логику и ограничения. **Нельзя заменить только импорт node:sqlite**.

## P0 — безопасность и авторизация
- [ ] Пользовательские и администраторские API должны доверять только проверенным Telegram initData; роли Owner/Co-Owner — только из серверной конфигурации; TOTP и rate limits обязательны.
- [ ] Проверить endpoint-by-endpoint права пользователя (включая поддержку, награды, admin, trade, referrals) и отклонение повторных/чужих operationId.
- [ ] Убедиться, что Supabase service_role и ключи Telegram/TOTP никогда не попадают в клиентские JS, логи, GitHub или Telegram URL.
- [ ] В Supabase **15 public таблиц с включённым RLS без политик** (наблюдение Supabase Security Advisor на 2026-11-11; severity INFO). При отсутствии политики обычные клиенты не проходят RLS; это не доказательство утечки. Шесть старых таблиц имеют grants anon/authenticated, но RLS по умолчанию запрещает операции. **Не отключать RLS ради исправления доступа.** Проверить серверный путь и минимальные полномочия.
- [ ] Перепроверить server logs на утечки персональных данных, обработку ошибок и защищённый backup/export. Отдельно проверять доступность support и начисление тестовых POINTS с настоящей 2FA.

## P1 — экономика и UX
- [ ] 200 уровней Mining: серверный расчёт +5…+1000%, проверка ежедневной эмиссии и платёжного источника.
- [ ] Daily Reward: непрерывная UTC-серия, рекорд, один Claim в день, идемпотентность, выдача строго из DAILY pool. GM milestones в тесте включаются **только** при GM_DAILY_MILESTONE_TEST=1. Дополнительные XP, временные бусты, рамки требуют отдельного серверного журнала и согласования.
- [ ] POINTS и Boxes: исполняемые сделки, лимиты выдачи, x1/x3/x5/x10 atomic payouts, дневной cap. Golden x10=1050 GM при cap=1000 GM сейчас не разрешён — не менять лимит без расчётов.
- [ ] Сундуки: текущие SVG+CSS дают только 3D-эффект. Для настоящих 3D-моделей нужны проверенные mesh/texture assets, budget GPU/CPU, low-end fallback, контроль размера загрузки.
- [ ] Market order book и все кнопки: Android 360px, Android 430px, Telegram iOS, светлая/тёмная тема, поворот/resize, отсутствие горизонтального скролла и перекрытия нижней панелью.
- [ ] Онбординг каждого раздела, включая POINTS и Boxes, должен указывать на реальные элементы и хранить факт прохождения.

## P0 — критерий запуска
- [ ] Production Mini App URL и токен текущего Telegram-бота сохраняются; тестовый бот не заменяет основной.
- [ ] Пройти CI, тест параллельных Claim/Trade/Boxes, независимый аудит уязвимостей и контроль бюджета эмиссии.
- [ ] Релизировать сначала в изолированный staging, проверить резервное восстановление; потом канареечное включение функций.
- [ ] Только после этих проверок готовить выпуск реального токена отдельно: требования площадок, контракт и права, безопасность, юридическая и налоговая экспертиза. Никаких обещаний доходности или смешения тестовой игровой экономики с настоящими активами.
